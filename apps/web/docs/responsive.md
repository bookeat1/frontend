# Адаптив сайта: контракт «мобильная версия — это приложение»

Дата: 2026-09-04. Ветка `docs/web-responsive-contract`. Задача T1.3.

Владелец сформулировал требование дословно: **«мобильная версия будет та, что в
мобилке, только надо её в веб перенести»**. Это значит, что источник правды для
узких экранов сайта — существующее приложение `apps/mobile` (Expo / React
Native), а не новый макет. Документ фиксирует, что именно и как переносится,
чтобы четыре следующие задачи (`chrome`, `home`, `catalog`, `venue`) делали
адаптив по одному правилу, а не каждая по своему.

Кода этот документ не меняет. Все ссылки на строки — на состояние `develop`
после слияния PR #125 (`53289bb`).

## 1. Лестница брейкпоинтов

`apps/web/tailwind.config.ts` **заменяет** `screens` (не `extend`), числа
берутся из `webLayout.breakpoints` в `packages/design-tokens/src/web.ts`:

| Префикс | Порог | Откуда число | Что задаёт структуру |
|---|---|---|---|
| (без префикса) | 0 – 767 | — | **мобильное приложение** (`apps/mobile/app/*`) |
| `md:` | 768 | макет, узел 3273:153 | мобильное приложение, две колонки в сетках карточек |
| `lg:` | 1024 | макет | **Figma WEB** (`3z0f6dgev4HMwBAHPjTjPo`), десктопная раскладка |
| `xl:` | 1280 | макет | Figma WEB |
| `2xl:` | 1440 | макет | Figma WEB, контейнер 1200 без боковых отступов |

Префикса **`sm:` в теме нет** — класс с ним молча выбрасывается (см.
`bugs/bookeat-web-sm-breakpoint-does-not-exist.md` в памяти команды). Пишем
только четыре имени из таблицы.

### Правило

**Числа из Figma WEB живут только под `lg:` и выше. Ниже `lg` структуру и
порядок блоков задаёт мобильное приложение.**

Обоснование:

1. Десктопный макет нарисован на 1440 с контейнером 1200 и не содержит ни
   одного кадра уже 1024. Всё, что мы «придумаем» для 360–1023, будет
   выдумкой — а у владельца уже есть проверенный на живых гостях ответ, как
   выглядит продукт на телефоне: приложение.
2. `lg` = 1024 — первая ширина, на которой десктопная раскладка физически
   помещается: две колонки заведения (основная + `w-venue-aside` 380),
   колонка фильтров `w-filters-rail` + выдача, панель поиска в одну строку
   (`lg:flex-nowrap`, `lg:h-panel`). Код сайта уже ломает раскладку именно
   на `lg` (`CatalogScreen`, `VenueScreen`, `FiltersRail`, `SearchPanel`,
   `Container`), менять этот порог значило бы переписывать работающее.
3. `md` (768) остаётся **промежуточным**, а не третьей системой: на планшете
   сохраняется мобильный порядок блоков, разрешено только раскладывать
   сетки карточек в две колонки (`md:grid-cols-2`) и класть широкую
   карточку выдачи горизонтально (`md:flex-row` в `VenueWideCard`). Никаких
   отдельных «планшетных» размеров шрифтов и отступов.
4. Внутри диапазона 0–767 **один набор размеров**: телефон 360 и телефон 414
   отличаются только шириной колонки, всё тянется. Это ровно то, как ведёт
   себя приложение (у него нет брейкпоинтов вообще).

Проверка на бумаге, что лестница выдерживает: контейнер на 360 — это
`360 − 2×16 = 328` px содержимого (`Container`: `px-4 lg:px-6 2xl:px-0`).
Приложение верстается под 390 с полями 16, то есть 358 — сайт на 360 уже
**у́же** приложения на 30 px, длинные русские слова проверяем именно на 360.

## 3. Что переносится дословно

### 3.1. Порядок блоков

Ниже `lg` порядок блоков на каждом экране — **ровно как в приложении**.

**Главная** (`apps/mobile/app/index.tsx`, строки 221–247):
`HomeHeader` (приветствие + город + строка поиска + капсула «Сегодня · 2 гостя»)
→ `RecommendedSection` («Выбрали для вас») → `CuisineSection` («Выберите
кухню») → `PromotionsSection` → `EventsListSection` (Афиша) → `ArticlesSection`.
На сайте (`HomeScreen.tsx`) сейчас: hero + `SearchPanel` → кухни → «Выбрали
для вас» → акции → каталог → афиша → гид → блок приложения. Ниже `lg` порядок
секций приводится к мобильному: **поиск → рекомендации → кухни → афиша →
статьи/гид**. Место ленты акций на главной сайта — см. § 8. Секция «каталог»
(`t.web.home.catalog`) и блок «скачайте приложение» мобильного аналога не
имеют; они остаются, но ниже всего мобильного порядка.

**Каталог** (`apps/mobile/app/search.tsx`, строки 245–320): строка поиска
`SearchBar` → ряд: `FilterButton` со счётчиком активных фильтров + чипы
ТОЛЬКО выбранных фасетов (каждый снимается тапом) → список. Сами фильтры —
в нижней шторке `FilterSheet`, не на экране. Пустой запрос показывает весь
каталог, а не заглушку.

**Заведение** (`apps/mobile/app/restaurant/[id]/index.tsx`, строки 100–235):
`VenueHero` → `SegmentedTabs` (Обзор / Фото) → `StoriesRail` → «О заведении»
→ `VenueScheduleCard` → «Из меню» (`ScrollableMenu` + кнопка) → «Контакты»
(иконки, адрес, `MapPreview`) → **прибитый к низу футер с единственной
кнопкой «Забронировать столик»**, ведущей на `/restaurant/[id]/book`.
Выбор слотов на экране заведения в приложении **не делается** — он живёт на
экране брони.

**Бронь** (`apps/mobile/app/restaurant/[id]/book/index.tsx`, строки 255–360):
`FlowHeader` → название и адрес заведения → `DateStrip` (лента дней) → две
пилюли (дата, гости) → секция «Время» (`SlotsSection`, вкладки Утро/Обед/Ужин)
→ «Пожелания» (`TextField`) → «Предзаказ» (на сайте отсутствует) → кнопка
«Продолжить» → отдельный шаг `confirm.tsx` (карточки: детали, пожелания,
контакт, подтвердить).

**Билет** (`apps/mobile/app/booking/[id]/index.tsx`, строки 292–430):
`ReservationHeaderCard` → ряд действий → `BookingDetailsCard` →
`WhatHappensNextCard` → уведомления/предзаказ. Одна колонка, карточки
во всю ширину.

**Вход** (`apps/mobile/app/auth/sign-in.tsx`, строки 427–560): заголовок →
поле телефона → кнопка → строка согласия; второй шаг: заголовок → «код
отправлен на …» → `OtpInput` → обратный отсчёт / «отправить ещё раз».
Это уже совпадает с `LoginScreen.tsx`; ниже `lg` переносится только
внешняя рамка (см. § 5, `chrome`).

### 3.2. Тексты и словари

Тексты берутся из `packages/i18n` **как есть**. Для разделов, которых на
сайте пока нет, словари уже готовы на трёх языках:

| Ключи | `ru.ts` | `kk.ts` | `en.ts` |
|---|---|---|---|
| `t.explore.*` (главная: `recommendedTitle`, `cuisineTitle`, `afishaTitle`, `articlesTitle`, пустые/ошибочные состояния) | стр. 90 | стр. 45 | стр. 42 |
| `t.afisha.*` | стр. 209 | стр. 120 | стр. 117 |
| `t.articles.*` | стр. 271 | стр. 131 | стр. 128 |
| `t.web.*` (всё, что уже на сайте) | стр. 3261 | стр. 2305 | стр. 2298 |

Новых ключей под адаптив не заводить: если на узком экране нужен текст,
которого нет в `t.web.*`, сначала ищем его в мобильном разделе словаря
(`t.explore`, `t.search`, `t.restaurant`, `t.booking`, `t.auth`) и берём
оттуда — на трёх языках сразу. `kk`/`en` отстают от `ru` по мобильным
ключам (см. `bugs/bookeat-frontend-kk-en-dictionaries-703-keys-behind.md`) —
перед использованием ключа проверить, что он есть во всех трёх файлах.

### 3.3. Семантика четырёх состояний

Каждый блок с данными имеет **загрузку, ошибку, пустоту, успех** — на сайте
это `src/components/state/AsyncBlock.tsx`, в приложении
`apps/mobile/src/components/StateViews.tsx` (`LoadingState` / `ErrorState` /
`EmptyState`). Переносится смысл, не разметка:

- Скелет загрузки той же высоты, что содержимое (страница не прыгает).
- Ошибка сети — с кнопкой «Повторить» (`t.common.retry`), это единственное
  место, где кнопка перезапроса уместна.
- **Пустой ответ — это норма, а не ошибка.** Решение зафиксировано в
  `apps/mobile/app/events.tsx` (строки 23–25, 61–75) и
  `apps/mobile/app/articles.tsx` (строки 34–36, 76): пустая афиша — это
  «ничего не запланировано», пустые статьи — «ничего не опубликовали».
  Пустое состояние **спокойное и БЕЗ кнопки перезагрузки**: кнопка лишь
  перезапросила бы ту же пустую ленту. Тексты: `t.explore.eventsEmptyTitle`
  / `eventsEmptyDescription`, `t.articles.emptyTitle` / `emptyDescription`.
  Переносится как есть; на сайте роль «потянуть, вдруг появилось» играет
  обычная перезагрузка страницы, отдельного жеста не нужно.
- У билета брони пустого состояния нет: id либо разрешается, либо это ошибка
  (404 — ошибка, `booking/[id]/index.tsx`, строки 10–12 комментария).

## 4. Что не переносится и почему

| Из приложения | Почему не переносим | Чем заменяем на сайте |
|---|---|---|
| Примитивы RN: `View`, `Text`, `StyleSheet`, `ScrollView`, `SafeAreaView`, `Pressable` | Это другой рантайм; сайт — Next.js + Tailwind, компоненты из `src/components/ui/*` | семантический HTML: `section`, `article`, `nav`, `button`, `a`; стили — утилиты Tailwind |
| `RefreshControl`, pull-to-refresh (17 экранов приложения) | Жест принадлежит нативному скроллу; в браузере у него уже есть штатная перезагрузка страницы и «Повторить» в состоянии ошибки | ничего; кнопки «обновить» в пустом состоянии НЕ добавлять (§ 3.3) |
| Мобильные токены `@bookeat/design-tokens` (`colors.ts`, `spacing.ts`, `typography.ts`, `fonts.ts`) | Они описывают экран 390 px в числах RN без единиц (`packages/design-tokens/src/web.ts`, строки 8–16). Сайт берёт **только** `web*`-экспорты из `packages/design-tokens/src/web.ts`. Если для узкого экрана нужен размер, которого в `web*` нет, — он добавляется новым полем в соответствующий `web*`-блок (например, `webHero.mobileTitleFontSize`) с ссылкой на мобильный экран как источник, а не импортом из `typography.ts` | `web*`-токены через `tailwind.config.ts` |
| Навигация `expo-router` (`Stack`, `useRouter`, `useLocalSearchParams`, `FlowHeader` с «назад/закрыть») | На сайте есть URL, история браузера и `next/link`; закрывать поток брони «крестиком» некуда — есть «назад» браузера и хлебные крошки | `Link`, `useRouter` из `next/navigation`, хлебные крошки `t.web.venue.breadcrumb*` |
| Нижняя навигация `BottomNavBar` (Обзор / Поиск / Брони / Гастрогид / Профиль) | «Обзор» и «Поиск» — это шапка, «Профиль» и «Брони» — страница `/profile` и её раздел, а «Гастрогид» на сайте не существует | шапка `SiteHeader` с бургером ниже `lg` (§ 5) |
| `HomeHeader` «под статус-баром» и `useNavBarSpacing` | На сайте нет статус-бара и нижней панели; отступы под них — мобильный артефакт | обычный поток документа |
| Нижние шторки с колесом (`WheelSheet`, `FilterSheet`, `partySheet`) как **компонент** | Реализация на `Modal` RN и жестах | `src/components/ui/Modal.tsx`; **поведение** (одно окно на выбор даты/гостей, черновой выбор до «Готово») переносится |
| Тактильный отклик (`expo-haptics`), `Share` системный | нет в браузере | — |
| Предзаказ (`book/menu.tsx`, степперы в `confirm.tsx`) | На сайте предзаказа нет по решению из `conventions/bookeat-web.md` («Поток бронирования») | — |

## 6. Как проверять

Ширины: **360, 414, 768, 1024, 1440.** Каждая — своя причина:

| Ширина | Зачем |
|---|---|
| 360 | Нижняя граница. Контент 328 px, у́же приложения (358). Длинные слова: «Средиземноморская», «Забронировать столик», названия заведений |
| 414 | Обычный телефон; проверяет, что ничего не «прилипло» к 360 фиксированными ширинами |
| 768 | Порог `md`: сетки 2 колонки, `VenueWideCard` ложится горизонтально, порядок блоков всё ещё мобильный |
| 1024 | Порог `lg`: включается десктоп — две колонки заведения, колонка фильтров, панель поиска в строку, шапка без бургера, `sticky` |
| 1440 | Порог `2xl`: контейнер 1200 без отступов, эталон Figma |

Как:

1. Скриншоты через `shot` (описано в `conventions/bookeat-web.md`, «Проверка
   вёрстки — `shot` + подсунутый localStorage») на всех пяти ширинах для
   каждого из шести роутов; **на 1024 и 1440 ничего не должно измениться**
   относительно `develop` — это критерий, что правки под `lg` не протекли
   вверх.
2. На 360 — `document.documentElement.scrollWidth === 360`: горизонтальной
   прокрутки страницы быть не должно (прокрутка **внутри** горизонтальных
   рядов — норма и ожидается).
3. Клавиатура: бургер, кнопка фильтров, прибитая панель брони, модал —
   доступны по Tab, закрываются по Esc, фокус видим.
4. Четыре состояния каждого блока на 360: скелет той же высоты, ошибка с
   «Повторить», пустота **без** кнопки, успех.
5. `pnpm --filter web exec tsc --noEmit`, линтер по изменённым файлам,
   `next build`, тесты в `__tests__` — как для любой правки сайта.
6. `grep -rno "\bsm:" apps/web/src apps/web/app` должен быть пуст.

## 7. Замечено попутно (не правил)

- `SiteHeader.tsx:77` — пункт `guide` ведёт на `/guide`, роута нет, 404.
  Решения по пункту нет (`conventions/bookeat-web.md`, «Временное скрытие
  пункта шапки»). При переделке шапки в бургер это станет заметнее: в меню
  на весь экран мёртвый пункт — второй сверху.
- `SiteFooter.tsx:48` — ссылки соцсетей `href="#"` с однобуквенной заглушкой
  вместо иконки; в бургер-шапке и подвале на телефоне это будет бросаться
  в глаза сильнее, чем на 1440.
- `HomeScreen.tsx` — в отличие от приложения, на главной сайта есть секция
  «каталог» (`t.web.home.catalog`) и лента акций (`t.web.home.promos`,
  данные из `lib/queries.ts:77`). Про акции — § 8; про каталог решения
  нет.
- В `apps/web/app/layout.tsx` нет явного `viewport`; Next.js App Router
  подставляет `width=device-width, initial-scale=1` сам, так что на телефоне
  сайт не масштабируется как «десктопный». Проверить одним скриншотом на
  360 перед началом задач, чтобы не искать проблему в CSS.
