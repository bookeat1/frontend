# BookEat Frontend — Architecture

Справочник по устройству фронтенд-монорепо: apps/mobile, apps/admin, apps/web,
packages/*. Не руководство агенту (это CLAUDE.md) и не список задач — то, что
меняется от недели к неделе, сюда не входит намеренно.

Бэкенд, инфраструктура, схема БД и API — в отдельном документе
`bookeat-backend/docs/ARCHITECTURE.md`. Дизайн-токены и паттерны UI —
в `docs/DESIGN_SYSTEM.md` в этом репозитории. Продуктовые требования —
в `bookeat-backend/docs/PRD.md`.

---

## Overview

BookEat — платформа бронирования столиков в Казахстане (Алматы, Астана). Гость
ищет заведение, выбирает слот, бронирует, при необходимости платит депозит или
предзаказывает блюда; заведение принимает бронь в своём кабинете и получает
уведомление; платформа ведёт контент (афиша, акции, гастрогид) и рассчитывается
с заведениями.

Одна картинка словами:

```
   Гость                        Персонал заведения           Оператор платформы
     │                                  │                            │
 apps/mobile (Expo/RN)          apps/admin (Next.js)         apps/admin (те же
 apps/web (Next.js)             Telegram mini app            экраны, роль admin)
     │                                  │                            │
     └──────────────┬───────────────────┴────────────────────────────┘
                    │  HTTPS, JSON, /api/v1, Bearer JWT
                    ▼
        ┌───────────────────────────────────────────────┐
        │  Go backend-core (Clean/Hexagonal)            │
        │  cmd/http  — REST API (Gin)                   │
        │  cmd/worker — фоновые задачи (outbox, SLA,    │
        │               реконсиляция, выплаты, синк)    │
        │  cmd/migrate — goose, отдельный шаг деплоя    │
        └───────┬───────────────┬───────────────┬───────┘
                │               │               │
        PostgreSQL 16      Внешние системы   Cloudflare R2
        (единственное      FreedomPay,       (медиа + бэкапы,
         состояние)        TipTopPay,         разные бакеты)
                           Kaspi-сервис,
                           Telegram, WhatsApp,
                           Expo Push, Geoapify,
                           Amplitude, legacy Supabase
```

Отдельно, вне Go-монолита, живёт **Kaspi Pay сервис** (Node + SQLite,
`82.41.30.21`): у Kaspi нет песочницы и устройство привязывается к кассиру, поэтому
он вынесен в самостоятельный мультитенантный сервис и общается с бэкендом по HTTP
и вебхуку.

### Что означает слово «прод»

Исторически «прод» означал две разные системы, и это регулярно путало людей:
старое приложение на Supabase и новый Go-бэкенд. **По проверке 2026-09-02
переключение уже произошло:** гость мобильного приложения ходит в
`backend.book-eat.com` → `213.155.20.76` → контейнер `deploy-postgres-1`
(PostgreSQL 16.6, база `bookeat`); `LEGACY_DB_URL` на проде закомментирован, то
есть боевой контур больше не читает Supabase. На тот момент на проде: goose 103
(88 применённых миграций), 46 заведений, 2462 позиции меню, 128 пользователей,
654 брони, ~23 МБ.

Старый проект Supabase (`wqwpreyqdmifcwftwnwe`) остаётся существовать и содержит
**похожие, но разошедшиеся** данные (44 заведения против 46, разный состав) —
считать его боевым нельзя. Правило: перед любой записью «в прод» сначала доказать
принадлежность базы — сверить `total` публичной выдачи `GET /api/v1/restaurants` и
`md5(description)` одного и того же `id`; совпасть должны и хэш, и счётчик
активных. Один хэш — не доказательство.

Легаси-синк (Supabase → новый Postgres) остаётся включённым **на тесте** и ходит
в офлайн-копию, а не в живую Supabase (см. решения по инфраструктуре).

### Баз данных четыре, не одна

| База | Где | Назначение |
|---|---|---|
| Основная (PostgreSQL 16) | контейнер `deploy-postgres-1` на прод- и тест-сервере | всё состояние Go-бэкенда; схема — миграции goose |
| Legacy Supabase | проект `wqwpreyqdmifcwftwnwe` | старая система; новый бэкенд только читал её односторонним синком, никогда не писал |
| Оффлайн-копия легаси | контейнер `legacy-postgres`, база `legacy_copy` на тесте | тест физически не может дотянуться до боевой Supabase |
| SQLite Kaspi-сервиса | `82.41.30.21`, `/opt/kaspi/app` | свои компании, кассиры, транзакции, вебхуки |

## Frontend (монорепо)

Репозиторий `bookeat-frontend`: pnpm-workspace (`apps/*`, `packages/*`), Node ≥ 20
(CI собирает на 22), **pnpm 10.34.5 обязателен** — обычным npm проект не
соберётся. Общие проверки на корне: `pnpm run typecheck` (tsc по всем пакетам),
`pnpm run lint`, `pnpm run test` (vitest), `pnpm run check` — то же, что гоняет CI
на каждый push и PR. Тесты лежат рядом с кодом в `__tests__`; правило — **фикс бага
приезжает вместе с тестом, который этот баг ловит**.

### `apps/mobile` — приложение гостя

Expo SDK 57, React Native 0.86, React 19, TypeScript, навигация `expo-router`
(файловый роутинг в `app/`: `restaurant/`, `booking/`, `events`, `promotions`,
`gastroguide`, `articles`, `favorites`, `profile`, `notifications`, `auth`,
`onboarding`, `search`, `city`). Данные — TanStack Query. Хранение токенов —
`expo-secure-store`. Пуши — `expo-notifications`. OTA и сборки — `expo-updates` +
EAS (`eas.json`).

Ключевая деталь слоя данных: экраны ходят за данными **только** через
`useRepository()` (`src/lib/repository.tsx`). Какая реализация активна, решает одна
переменная окружения:

- `EXPO_PUBLIC_API_URL` задана → `HttpRestaurantRepository`, живой бэкенд;
- не задана → `MockRestaurantRepository`, выдуманные данные.

Обе реализуют один интерфейс, поэтому ни один экран не знает, с кем разговаривает.
Практическое следствие: приложение без `.env` молча показывает несуществующий
каталог — это регулярная причина ложных багрепортов.

**Ловушка профилей EAS:** профиль `production` в `eas.json` смотрит на **тест**;
на прод смотрит только `production-main`.

### `apps/admin` — кабинет заведения и панель платформы

Next.js 15, React 19, Tailwind, TanStack Query. Собирается как **статический
экспорт** (`output: 'export'`) — сервером Next нигде не запускается. Один и тот же
код обслуживает две роли: менеджера конкретного заведения и суперадмина
платформы; что показать, решает роль в токене и ответы API.

Вход — **email + пароль** (`POST /api/v1/auth/login`), а не OTP: у персонала нет
проблемы «телефон под рукой», зато есть общий доступ с рабочего места. (В памяти
команды есть противоречащая запись того же дня, называющая вход OTP; авторитетной
считается проверенная кодом версия с паролем.)

`basePath` различается по контурам: на тесте панель живёт по подпути
`/admin-preview`, на проде — на своём домене `admin.book-eat.com` с **пустым**
basePath.

Историческая особенность: UI кабинета сознательно тоньше API — часть полей,
существующих в API и БД, долго не имела формы. Нельзя предполагать, что раз есть
ручка, значит есть и экран: проверять оба слоя отдельно.

### `apps/web` — десктопный сайт

Next.js 15, тот же стек, порт 3100. Страницы: витрина заведений (`venues`),
`events`, `promos`, `guide`, `articles`, `bookings`, `profile`, `login`, плюс
платформенные страницы (`about`, `how-it-works`, `contacts`, `jobs`, `offer`,
`privacy`, `cancellation`) и витрина компонентов `/kit`.

В отличие от админки, **веб разворачивается как Node-контейнер**, а не статикой:
маршрут `app/venues/[id]` динамический без `generateStaticParams`, статический
экспорт на нём физически не собирается.

### `packages/*` — общий код

- **`@bookeat/api`** — единственный слой знаний об HTTP-контракте бэкенда: типы
  (`types.ts`), интерфейс репозитория (`repository.ts`) и две его реализации
  (`http-repository.ts` / `mock-repository.ts`), низкоуровневый клиент
  (`http-client.ts`, `client.ts`), маппинг ответов (`http-mapping.ts`), отдельная
  точка входа для админских ручек (`./admin`), помощники по расписанию, статической
  карте, времени суток. Отдельный файл `unknown-data.ts` перечисляет по полям, чего
  в API ещё нет: правило — **если данных нет, приложение говорит «не знаю», а не
  придумывает правдоподобное значение**. Тестами покрыт именно этот пакет плотнее
  всего (~40 файлов в `__tests__`) — это граница, на которой ломается совместимость
  с сервером.
- **`@bookeat/design-tokens`** — цвета, отступы, типографика. Числовые значения
  берутся из Figma, не «на глаз» с работающего экрана.
- **`@bookeat/i18n`** — словарь интерфейса.
- **`@bookeat/markdown`** — рендер markdown (react-markdown + remark-gfm) для
  статей и платформенных страниц в `admin` и `web`.

Мобильное приложение потребляет `api`, `design-tokens`, `i18n`; `admin` и `web` —
те же плюс `markdown`.

## Ключевые архитектурные решения (фронтенд)

### Контент, переводы, кабинет

- **Порядок выката: сервер всегда раньше клиента.** Бэкенд трактует карту
  `*_i18n` как полную замену, а новая админка шлёт частичный патч — выложи панель
  раньше сервера, и каждое сохранение перевода молча стёрло бы английский текст.
  Тот же порядок уже спасал раньше. Прод трогается только по отдельной команде
  владельца, даже если тест зелёный давно. *(Подтверждено как жёсткое правило
  2026-08-30.)*
- **Кухни: справочник `cuisines` + `restaurant_cuisines` (M:N) + `cuisine_aliases`;
  колонка `restaurants.cuisine_type` не удаляется**, а становится вычисляемым
  перечислением названий через запятую — контракт обратной совместимости для уже
  опубликованной магазинной сборки. Составные строки не разбиваются автоматикой
  («Японская (идзакая)» — одна кухня). *(ADR-022.)*
- **Синк со старой системой перестал владеть городом и кухней.** У таблицы
  `restaurants` **две** двери — `legacysync.UpsertRestaurant` и `cmd/etl`; забирая
  колонку под кабинет, закрывать нужно обе одновременно (один раз забыли — пришлось
  чинить отдельным PR). *(ADR-023.)*
- **Контент платформы:** `events.restaurant_id` / `promos.restaurant_id` nullable,
  `NULL` = публикует платформа, авторизация через глобальную роль, а не через
  ростер заведения. Платное событие платформы запрещено и в БД (CHECK), и в
  usecase (422): получатель платежа всегда заведение. *(ADR-024.)*
- **Справочник городов: `city_id` рядом со строкой `city`, синхронизацию держит
  триггер БД.** Неизвестный город из старой системы принимается и помечается на
  разбор, но **в справочник автоматически не заводится** — иначе опечатка станет
  постоянной справочной записью, которую потом можно только скрыть. *(ADR-026.)*
- **Удобства: свободнотекстовая `restaurant_features` удалена в пользу справочника
  `venue_features`; фильтр по И, не по ИЛИ.** Кухня — это выбор (OR), удобства —
  требование (AND). Синонимы заводятся только из реальных написаний, не по
  догадке. *(ADR-027, подтверждено.)*
- **Числовые значения интерфейса — всегда из Figma**, никогда «на глаз» с
  работающего экрана: подгонка чисел под уже отрисованный экран однажды развела
  заголовки между собой на месяцы.


### Мобильное приложение

- **`develop` — мейнлайн мобильного фронтенда** (после инцидента с почти-OTA от
  устаревшей ветки); `feat/stories-frontend` сохранён как зеркало, но ретирен.
- **Локальный список стран вместо `libphonenumber-js`** — 3.5 КБ gzip против
  19–40 КБ, а русских названий стран библиотека всё равно не содержит.
  *(ADR-017.)*
- **Признак «местный/турист» — только явный ответ гостя.** Вывод из телефона
  негоден (`toE164` жёстко добавляет +7 любому номеру), локаль устройства
  недостоверна. *(ADR-016; сама реализация вопроса ещё не сделана.)*
- **Полностью безголовая сборка и сабмит iOS через EAS невозможны** — это
  ограничение eas-cli, а не конфигурации BookEat: distribution-сертификат и
  карточку в App Store Connect нельзя создать неинтерактивно. *(ADR-019.)*
- **Android: package в Google Play (`kz.bookeat.app`) разошёлся со сборкой
  (`com.bookeat.app`)** — открытый блокер, решение не принято. Заливать текущую
  сборку в существующую карточку нельзя: получится второе приложение, а не
  обновление.
