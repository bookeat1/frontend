# BookEat — Design System

Накопительный справочник дизайн-системы платформы бронирования столиков (Казахстан, RU/KZ аудитория).
Источники: `packages/design-tokens/` (первоисточник правды по токенам) и спеки в `/home/tai/work/design-specs/{web,gastroguide}/*.md`
(снятые REST/MCP-запросами к Figma). Здесь — только стабильные, повторяющиеся факты об устройстве UI.
За точными пиксельными размерами конкретного экрана — в файлы `design-specs/*`, ссылки в конце.

---

## Токены

Пакет `packages/design-tokens/src/`: `colors.ts`, `typography.ts`, `spacing.ts`, `fonts.ts` — токены **мобильного
приложения** (React Native, числа без единиц); `web.ts` — токены **десктопного веба** (Tailwind/CSS, px).
Это два разных файла осознанно (см. комментарий в начале `web.ts`): мобильный экран 390px с ролевыми именами
токенов vs веб-кит с нейтральной лестницей 0…900 и сеткой 1440. Пересечение — `brand.primary`/`brand/500`
(`#B33036`) и `text.brand`/`brand/600` (`#96272C`) — одна и та же марка на обеих платформах.

### Цвета — мобильное приложение (`colors.ts`)

Именование по РОЛИ, а не по значению — «менять надо один токен, а не искать все места с этим hex».

- **brand**: `primary #B33036` (CTA, активный таб, пин карты), `favorite #B33036` (залитое сердечко).
- **text**: `primary #1B1B1B`, `muted #A5A5A5`, `mutedStrong #7D7D7D`, `brand #96272C` (подпись чипа на бордовой
  подложке — не `brand.primary`, там контраст ниже), `subtitle #171717`, `strong #000000` (цена в меню),
  `onDark #FFFFFF` / `onDarkMuted rgba(255,255,255,.85)` (текст на фото), `navInactive #595959`.
- **background**: `screen #F5F5F5` (фон экрана) vs `surface #FFFFFF` (карточка/лист) — это ключевая пара:
  экран чуть темнее подложки карточек. `subtle #F8F8F8` — приглушённый блок НА белом (светлее экрана, т.к.
  лежит поверх, а не под). `chip #F1F1F1` / `chipAlt #F3F2F2` — нейтральные пилюли. `chipActive #1B1B1B`.
- **status** (пилюля статуса брони): pending `#F67700`/`#FFE4CC`, positive `#16A34A`/`#D7F9E3`,
  negative `#FF323B`/`#FFE9EA`, neutral `#7D7D7D`/`#F1F1F1`. Контраст текст/подложка у всех трёх ниже 4.5:1 —
  это значения макета, не наш выбор.
- **guide** / **brand2**: отдельные палитры для гастрогида («Editorial v2», кремовый лист + золото) и для
  фирменной страницы бренда внутри гастрогида (Ocean Basket — тёмно-синий + золото). Не подмешиваются в
  общие роли — это осознанно другой визуальный язык для конкретного раздела/бренда, не вся платформа.
- **overlay**: набор именованных градиентов/скримов для текста поверх фото — единого «одного скрима на всё»
  нет, плотность и число стопов зависят от объёма текста и яркости фото под ним (см. `listCardScrim*` —
  3 стопа, `photoFlatScrim` — сплошная заливка для карточки с текстом и сверху, и снизу).
- Прозрачный конец градиента ВСЕГДА тот же цвет с alpha=0, а не CSS `transparent` — на iOS `transparent`
  даёт серую кайму по краю перехода. Системное правило, применено во всех overlay-градиентах.

### Цвета — веб (`web.ts`, `webPalette`/`webColors`)

Нейтральная лестница `neutral0…900` + акценты `brand500/600/50`, `success/warning/danger` (50/500/700-подобные
пары «заливка/текст»). Семантические алиасы `webColors.background/border/text/overlay.*` поверх лестницы,
имена — как подписано в Figma-ките (`background/canvas`, `text/secondary`, `border/strong`…).

Задокументированная ловушка: **имя переменной в Figma и имя токена в коде иногда совпадает, а значение —
нет** (напр. `border/default` в ките = `#E7E7E7`, но тот же ярлык на карточке заведения — фактически
`#DADADA`, т.е. `border/strong` по значению). Правило: переносить **число**, имя переменной макета сверять
отдельно, не доверять напрямую.

### Типографика

Мобильное приложение — шкала ролей `titleXxl…caption` на Noto Sans (Regular/Medium/SemiBold/Bold), плюс
акцентные засечные гарнитуры для конкретных ролей:
- **Playfair Display Bold Italic** — только имя заведения (карточка списка, шапка карточки заведения) и
  название события (афиша). Не используется больше нигде.
- **Playfair Display Italic** (не Bold) — заголовки гастрогида.
- **Cormorant Garamond Bold** / **Montserrat** (Regular/Medium/SemiBold/Bold) — только на фирменной странице
  бренда (Ocean Basket) внутри гастрогида.

Правило платформы: типографика — это роль (`titleSection`, `body`, `caption`…), не «кегль+вес» напрямую в
компоненте; один кегль на семантически одинаковые заголовки одного экрана (см. кейс `titleSection`:
рассинхрон 20 vs 17 на главной несколько раз чинили и откатывали — сейчас единая роль на все заголовки секций
главной и гастрогида).

Веб — отдельная шкала `webTypography.display/h1/h2/h3/titleL/bodyL/bodyM/bodyS` (Noto Sans, вес числом, не
именем), плюс **много одноразовых наборов кегль/интерлиньяж под конкретный узел** (`webHero.titleFontSize`,
`webVenuePage.mosaic`-заголовки и т.д.) — в вебе типографика ощутимо менее унифицирована в шкалу, чем в
мобильном приложении: почти на каждом крупном блоке страницы (герой, карточка заведения, билет брони,
профиль) свой набор кегль/лайн-хайт/трекинг, снятый с конкретного узла, а не взятый из `webTypography`.

### Spacing / радиусы / контролы (мобильное, `spacing.ts`)

- Базовая шкала отступов 4pt: `none 0 → xxs 2 → xs 4 → sm 8 → md 12 → lg 16 → xl 20 → xxl 24 → xxxl 32 → huge 40`.
  Числа НЕ из шкалы (14, 18, 22, 28...) в токенах явно помечены комментарием «это значение макета» — не
  округлять до шкалы, если так нарисовано.
- Радиусы именованы по РОЛИ, не по значению, даже если значения совпадают (`card 20`, `dialog 24`,
  `contentBlock 24`, `homeSection 24`, `guideCard 24` — четыре токена по 24, каждый свой, чтобы правка одной
  роли не потянула остальные). `pill 999` — чипы/пилюли/кнопки-иконки/поле поиска.
- `hitSlop.minTouchTarget = 44` — жёсткое правило доступности; там, где визуальная высота контрола меньше
  (чип 40, компактная пилюля карточки 28), зона касания добирается hitSlop'ом, а не раздутым визуалом.
- `controlHeight`: единые высоты по роли элемента через весь каталог — пилюли выбора даты/гостей/время-слота
  и sticky CTA все 48; чип-фильтр под поиском 40; статус-пилюля 32.

### Web layout (`web.ts`)

- Сетка: контейнер `1200`, внешние поля `120`, 12 колонок по 76, гаттер 24, брейкпоинты `1440/1280/1024/768`.
- `webRadius`: `sm 8` (слоты/бейджи) → `md 12` (поля/кнопки M) → `lg 16` (карточки блюд/кнопки L) →
  `xl 20`/`card 24` (карточки заведений — в ките подписано 20, реальные карточки нарисованы 24, расхождение
  задокументировано отдельным токеном, не скрыто) → `xxl 24` (модалки/тикет) → `full 999`.
- Карточка заведения (`webVenueCard`) — единственная карточка веба, полностью размеченная в ките: 282 шир,
  фото 190, паддинг тела 16, двойная тень `0 4px 10px -2px + 0 2px 4px`, слот-подсказка 32/радиус 10, кружок
  избранного 40 с отступом 12.
- Компоненты кита (`webControls`): `buttonL 54/r16`, `buttonM 42/r12`, `chip 38/r999`, `slot 42/r12`,
  `input 48/r12`, `badge 32`. Многие реальные экраны используют СВОИ размеры кнопок/полей, отличные от кита
  (форма входа: инпут 52 вместо 48, кнопка «Войти» в шапке 48 вместо 42/54) — это не ошибка, а сознательно
  задокументированное расхождение конкретного узла с общим китом; при переносе в код нужно смотреть, из
  какого именно узла считан размер, не подставлять кит по умолчанию.

## Принципы

Подтверждено спеками, а не придумано:

1. **Источник правды — Figma, не глаз.** Правило владельца от 26.08.2026: значения снимаются с конкретного
   узла REST/MCP-запросом, комментарий у токена содержит id узла. Расхождения с макетом (когда решение
   владельца/CEO намеренно отличается от узла — напр. `titleSection` 17/24 вместо нарисованных 20/28)
   документируются явно в коде, а не «тихо чинятся» при следующем ревью макета.
2. **Роль важнее значения.** Токены именуются по смыслу использования (`background.subtle`, `radius.dialog`),
   а не по цвету/числу — даже когда два токена совпадают по значению, они остаются раздельными, если играют
   разные роли (пример: четыре разных токена радиуса со значением 24).
3. **Плотная, карточная типографика с одним акцентным засечным шрифтом.** Основной текст всей платформы —
   Noto Sans (гротеск), засечные гарнитуры (Playfair Display, Cormorant Garamond) — исключительно для имени
   заведения/события и для журнального раздела «Гастрогид»; смешение по всему каталогу не встречается.
   Кириллица в засечных файлах проверена явно (комментарий про cmap-таблицу) — важно при добавлении новых
   акцентных начертаний.
4. **Скругления и мягкие тени вместо обводок.** Карточки почти везде без явной обводки, со сплошной заливкой
   и мягкой тенью (веб: `0 4px 10px -2px rgba(0,0,0,.1)` + `0 2px 4px rgba(0,0,0,.05)`); обводка появляется
   точечно — на активных полях, на карточках гастрогида/бренда с более «журнальным» видом и на состоянии
   «выбрано».
5. **Изображение как основной носитель текста.** Крупные карточки (события, промо, гид, шапка заведения)
   несут название и мету ПОВЕРХ фотографии через именованный вертикальный градиент, а не в отдельном белом
   блоке под фото — паттерн, повторяющийся во всех «журнальных»/«витринных» списках приложения.
6. **Figma-макеты систематически не рисуют состояния.** Почти каждый файл `spec-*.md` заканчивается разделом
   «Чего в макете НЕТ», и по всем спекам повторяется один и тот же набор пробелов: нет skeleton/loading, нет
   пустого состояния («не найдено», карточка без избранного), нет состояния ошибки, нет hover/active/disabled
   для интерактивных элементов, не нарисован сценарий «бронь отклонена/недоступно». Из этого следует
   практическое правило команды: **все четыре состояния async-поверхности (loading/empty/error/success)
   всегда доделываются инженером** из существующих примитивов (`AsyncBlock`, `Skeleton`, `StateMessage` на
   вебе) — это не забывчивость дизайнера, это системный пробел макетов, ожидаемый по умолчанию.

## Паттерны компонентов

### Карточка заведения (venue card)

Повторяется с вариациями на: главная (сетка 4 в ряд и горизонтальный ряд), «Все заведения», страница
фильтра (широкий вариант), избранное, карточка списка в мобильном приложении.

Общая анатомия: фото сверху (радиус только у контейнера/карточки целиком, не у самого `<img>`) → кружок
«в избранное» абсолютным позиционированием в углу фото (сердце-обводка не в избранном / залитое
brand-цветом в избранном) → бейдж поверх фото («Столики сегодня» на тёмной плашке) → тело: название +
мета-строка (кухня · ₸-уровень · расстояние) → ряд из 2–3 «слотов» свободного времени, где первый/выбранный
слот — заливка `brand/50` + текст `text/brand`, остальные — нейтральная подложка `background/subtle` +
`text/primary`. Мобильный список (`listCard`) — вариант той же идеи, но подпись лежит НЕ под фото, а поверх
него по нижнему градиенту (см. принцип 5), высота карточки фиксирована (не пропорция от ширины) — на разных
экранах пропорция дала бы разные высоты, а в макете нарисовано конкретное число.

Широкая карточка (страница фильтра/поиска) — та же анатомия, развёрнутая горизонтально: фото слева, тело
справа с добавленным абзацем описания и рядом из 4–5 слотов вместо 2–3, ссылка «Все слоты» справа от ряда.

### Карточка события/афиши

Отдельный от venue card паттерн, хоть и похожий габаритами: фото занимает бОльшую долю карточки, дата
вынесена отдельной крупной плашкой (число крупно + месяц мелко капсом с трекингом) в углу фото, один
тег-бейдж категории (не ряд удобств, как у заведения). На вебе название/мета лежат ПОД фото в белом теле; в
мобильном приложении (карточка списка «Афиша», карточка-герой афиши) — название лежит ПОВЕРХ фото курсивным
Playfair Display, тем же приёмом градиента, что у карточки списка заведений. Высота карточки на вебе строго
одинакова у всех карточек ряда (в отличие от предположения «размер разный» — по факту макет всегда рисует
идентичные габариты в рамках одного ряда).

### Чипы / фильтры

Два принципиально разных вида чипа, которые нельзя путать (задокументировано явно в токенах и в спеках):

1. **Чип-переключатель фильтра** (ряд «Все / Рестораны / Кофейни…», активные фильтры на странице выдачи) —
   всегда pill-радиус (999), высота ~38–40, выбранный — сплошная заливка `brand.primary`/`background/brand`
   с белым текстом, невыбранный — светлая нейтральная подложка. Ширина по тексту, не фиксированная.
2. **Чип-метка внутри карточки** (тег категории, чип удобства «Терраса», «Парковка») — светлая/приглушённая
   подложка (нейтральный серый ИЛИ фирменный цвет с прозрачностью ~15%), текст приглушённого/фирменного
   тёмного оттенка; это не интерактивный переключатель, у него нет состояния «выбран/не выбран».

Активный применённый фильтр в списке результатов — третий подвид: та же pill-форма, но с крестиком «снять»
справа и текстом фирменного цвета на белой подложке; рядом всегда текстовая ссылка «Сбросить всё».

Круг «кухня» в горизонтальном скролле («Выберите кухню») — отдельный паттерн: круглое фото + подпись под ним
в одну строку без переноса (важно для длинных русских названий кухонь — см. платформенные различия ниже).

### Модалки / шторки (sheet)

- **Мобильное приложение**: нижняя шторка (bottom sheet) — скруглены только верхние углы (16 у стандартной
  шторки выбора даты/гостей, 24 у шторки welcome-drink/фирменной страницы), ручка-полоска 40×4 радиуса 4 по
  центру сверху с отступом ~6, затемнение экрана позади — обычно `rgba(0,0,0,0.35–0.45)` в зависимости от
  того, на каком фоне лежит шторка (темнее для белого экрана, легче для уже тёмной подложки). Контент внутри
  — вертикальный стек без внутренних скруглений у дочерних блоков, кроме собственных карточек внутри шторки.
- **Веб**: модалка — центрированное окно (не bottom sheet), радиус 24, паддинг 32, тень
  `0 20px 50px rgba(0,0,0,.32)`, скрим фона `rgba(27,27,27,0.72)` — заметно темнее мобильного скрима шторки.
- **Аккордеон** (главы истории бренда) — общий паттерн сворачивания: карточка со своим радиусом/обводкой,
  свёрнутое и раскрытое состояние отличаются ТОЛЬКО высотой и наличием тела с картинкой; фон, обводка, цвет
  текста, шеврон не меняются между состояниями (в снятых узлах шеврон даже не поворачивается — если нужен
  поворот при раскрытии, это решение инженера, макет его не рисует).

### Кнопки

Именование по роли, не по цвету: **Primary** (сплошная заливка brand), **Secondary/Ghost** (без заливки,
обводка `border/strong`/`border.control`, текст обычно `text.primary` или `text.brand`). На вебе размеры
кнопок закреплены в ките (`buttonL 54/r16`, `buttonM 42/r12`), но многие экраны используют собственный размер
под конкретный узел (кнопка входа в шапке, «Найти» в поиске, CTA на билете брони) — это ожидаемое расхождение
с китом, а не ошибка вёрстки; конкретное число нужно всегда сверять с узлом этого экрана, а не с общей
таблицей кита.

### Бейджи / статусы

Единый паттерн пары «светлая подложка + тёмный текст того же оттенка» на все статусы: success (зелёный),
warning (жёлтый/оранжевый), danger (красный), neutral (серый) — используется и в пилюле статуса брони
(мобильное приложение и веб-профиль: «Подтверждено», «Ждём подтверждения», «Завершено», «Отменено»), и в
информационных бейджах на фото карточек («Столики сегодня» — исключение, тёмная плашка вместо светлой, т.к.
лежит поверх фото, а не на белом теле). Заливка и текст статуса иногда берутся из РАЗНЫХ по насыщенности
ступеней одной палитры (напр. заливка `success/50`, а текст на бейдже темнее подписанного в ките
`success/500` — реальный текст `success/700`) — при переносе в код ориентироваться на сам бейдж в узле, а не
на образец переменной в общей палитре кита.

### Сегментированный контрол (segmented control)

Переключатель вкладок внутри раздела (профиль: «Активные/Прошедшие/Отменённые», страница фильтра:
«Списком/На карте») — общий вид: серая подложка-«дорожка», выбранный сегмент — белая заливка + мягкая тень
контрола, невыбранные — прозрачные с приглушённым текстом.

## Платформенные различия (mobile app vs web)

- **Токены полностью раздельные** (`colors`/`typography`/`spacing` для RN vs `web*` для сайта) — это
  осознанная архитектура пакета, не дублирование по недосмотру (см. комментарий в начале `web.ts`).
- **Типографическая шкала веба менее унифицирована**: мобильное приложение держит закрытый список именованных
  ролей (`titleXxl…caption`), почти каждый крупный узел веба (`webHero`, `webVenuePage`, `webBookingTicket`,
  `webProfile`) несёт свой одноразовый набор кегль/лайн-хайт вместо переиспользования `webTypography`.
- **Карточка списка**: в приложении подпись лежит ПОВЕРХ фото (градиент+курсив), на вебе — ПОД фото в белом
  теле карточки (кроме афиши/промо/гида на главной странице веба — там та же логика «поверх фото», что и в
  приложении). Ниже breakpoint `lg` веб явно наследует пропорции и радиусы у мобильных карточек (см. серию
  комментариев «НИЖЕ `lg`» в `web.ts`, ссылающихся на `apps/mobile` компоненты) — контракт `apps/web/docs/responsive.md`.
- **Bottom sheet — только в приложении**; веб для тех же сценариев (вход, подтверждение) использует
  центрированную модалку. Обратного (веб-модалка → мобильная шторка) в спеках не встречается.
- **Скролл длинных горизонтальных рядов** (кухни, чипы фильтра) одинаково устроен на обеих платформах:
  ряд шире контейнера — скроллится вбок, а не переносится/сжимается; на вебе это решение принято намеренно
  по аналогии с приложением, а не унаследовано автоматически (см. `webCuisineTile` — короткий период с
  уменьшенным кругом 64 отменён именно по этой причине).
- **Длинные русские слова в кухнях/названиях**: ширина ячейки-кружка кухни в обоих случаях подстраивается
  под ОДНО слово подписи без переноса (мобильное — `adjustsFontSizeToFit`, сжатие шрифта; веб — ячейка `HUG`
  по содержимому, круг остаётся фиксированного диаметра). Это единственное явно описанное в токенах решение
  проблемы «длинное русское слово ломает сетку» — стоит держать в голове как образец при вёрстке других
  списков с непредсказуемой длиной русского текста (RU/KZ аудитория, длинные слова — системный риск).
